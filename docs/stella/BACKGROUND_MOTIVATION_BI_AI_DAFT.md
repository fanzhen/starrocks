# StarRocks 集成 Daft 能力的 Background & Motivation

> 目的：为“在 StarRocks 中编排结构化 SQL 能力与 Daft 算子能力”提供可用于立项评审的背景与动机说明。  
> 范围：聚焦 BI + AI 数据准备与检索协同，不讨论预算、人力与排期。

---

## 1. 背景：AI 数据准备成为主战场

在生产环境中，AI 效果与迭代速度越来越受制于数据准备阶段，而不是仅受制于模型本身。典型流程包括：

- 结构化数据清洗与特征加工；
- 非结构化文本/多模态数据预处理；
- 检索召回与相关性打分；
- 结果回写与分析复盘。

业务团队已经形成 Python + DataFrame（Daft）开发习惯，因此目标不是“强推纯 SQL”，而是保留 Python 体验并补齐生产级能力。

---

## 2. 问题：仅在 Daft 中直接做，为什么不够

Daft 在灵活性与开发效率上很强，但在 BI + AI 一体化生产场景中，常见问题是：

1. **语义分叉**：AI 流水线与 BI 报表分别维护口径，Join/过滤/窗口定义不一致。  
2. **生命周期割裂**：数据写入、索引更新、compaction 后一致性难在同一平面验证。  
3. **可观测不足**：检索耗时、召回行数、排序行为缺少统一观测口径。  
4. **复现困难**：脚本化链路多，版本与状态回放成本高。  
5. **组织复用差**：单团队 POC 易成功，多团队长期协作易碎片化。

因此问题不在“Daft 能不能做”，而在“能否把 Daft 能力平台化并纳入统一数据语义与治理”。

---

## 3. 动机：为什么要在 StarRocks 内协同 SQL + Daft

项目目标是：

- 保留 Daft/Python 入口与算子灵活性；
- 把结构化语义、检索语义、生命周期一致性与可观测性收敛到同一引擎；
- 将“脚本可跑”升级为“生产可复现、可治理、可规模化”。

对于当前 Tantivy 方向，已有能力（`MATCH_ANY/ALL/PHRASE/PHRASE_PREFIX/REGEXP`、`TOKENIZE`、`BM25`、Profile 指标、compaction 一致性、benchmark）正好提供了这套收敛基础。

---

## 4. BI + AI 实际工作流示例

以下示例重点回答：**为什么不能只在 Daft 中做完，必须在同一引擎内协同结构化表与检索/算子能力。**

### 示例 1：客服 Copilot（AI）+ SLA 运营看板（BI）

**工作流**

- Daft 清洗工单文本、做摘要与实体抽取（产品线、错误码）。
- 数据回写结构化事实表 + 全文字段。
- SQL 执行 `MATCH_PHRASE` / `MATCH_REGEXP` 检索相似工单，`BM25` 排序。
- 与 `tenant/region/sla_level` 维表 Join，输出 SLA 报表。

**Daft-only 痛点**

- 检索逻辑和 BI 指标口径分离，容易出现“模型命中正常、报表解释冲突”。
- 压缩/合并后状态一致性难统一验证。

**同引擎必要性**

- 检索 + 关联 + 聚合在同一查询平面，语义一致。
- 可依赖 compaction 前后一致性验证保障回放可信。

### 示例 2：中文内容推荐召回（AI）+ 内容运营分析（BI）

**工作流**

- Daft 生成标签、主题向量、质量标签。
- StarRocks 建中文倒排索引（`parser=chinese`）。
- 召回用 `MATCH_ANY` / `MATCH_PHRASE`，排序用 `BM25 + 结构化特征`。
- BI 复盘曝光、CTR、覆盖率。

**Daft-only 痛点**

- 分词规则与 BI 分析口径容易脱节。
- 性能瓶颈与召回异常缺少统一可观测信号。

**同引擎必要性**

- `TOKENIZE()` 可直接调试分词行为，减少语义黑盒。
- `TantivyQueryTime` / `TantivyQueryRows` 可做统一排障与调优。

### 示例 3：风控事件检索（AI）+ 合规审计（BI）

**工作流**

- Daft 做事件文本标准化与标签补全。
- SQL 执行 `MATCH_ALL`（多关键词）+ `MATCH_REGEXP`（规则表达）。
- 与交易事实表做结构化关联，输出命中明细和审计统计。

**Daft-only 痛点**

- 规则检索与事实关联分散在脚本层，审计回放复杂。
- 规则变更后历史口径难统一回溯。

**同引擎必要性**

- 检索与审计共享语义层，合规链路更完整。
- Profile + benchmark 支撑规则上线后的持续观测。

### 示例 4：RAG 数据准备（AI）+ 知识资产治理（BI）

**工作流**

- Daft 完成 chunk、去重、元数据增强。
- StarRocks 做增量入库、倒排索引维护。
- `MATCH_PHRASE_PREFIX + BM25` 输出候选文档。
- BI 评估覆盖率、命中率、内容老化率并驱动刷新。

**Daft-only 痛点**

- 数据与索引生命周期割裂，增量后一致性验证薄弱。
- 召回质量变化与数据状态变化难统一复盘。

**同引擎必要性**

- 可通过“写入-检索-compact-再检索”闭环约束索引漂移风险。
- 可基于统一基准持续评估性能与质量边界。

---

## 5. 结论（可直接用于汇报）

本项目不是要替代 Daft，也不是要求业务方改写为纯 SQL。  
核心是：**在保持 Python/DataFrame 开发体验不变的前提下，把全文检索语义、结构化分析语义、数据生命周期治理收敛到同一引擎，形成可复现、可观测、可规模化的 BI + AI 数据准备与检索能力。**
